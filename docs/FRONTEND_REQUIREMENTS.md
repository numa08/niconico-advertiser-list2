# フロントエンド要件定義（EARS記法）

Kobweb（Compose for Web / Kotlin/JS）で実装されている現行フロントエンドの仕様を、実装コードから抽出して EARS 記法で整理したもの。React への再実装時の受け入れ基準として使う。

- **対象**: `site/src/jsMain/**`（画面・状態・スタイル）、`site/src/commonMain/util/*Extractor.kt`（入力バリデーション）、`site/build.gradle.kts` の `kobweb.app.index`（head / OGP / GA4）
- **対象外**: バックエンドAPIの仕様。API契約は [WORKERS_API_SPEC.md](./WORKERS_API_SPEC.md)（詳細仕様）および [CLOUDFLARE_MIGRATION.md](./CLOUDFLARE_MIGRATION.md) §4 の項目1〜11（完了条件）が正であり、本書はその**呼び出し側**の責務のみを定義する。特に広告履歴は継続カーソル方式（WORKERS_API_SPEC.md AH-2〜AH-4）であり、全件の結合はフロントエンドの責務である（FE-070a）
- **位置づけ**: 本書は CLOUDFLARE_MIGRATION.md §4 の項目12〜16（フロントエンド）を展開・詳細化したもの
- **原典**: 記述は原則として実装コードを正とする。ただし付録Aに挙げた既知の不具合については**修正後の仕様**を要件として記述している（対応方針は決定済み）。README.md の機能説明と食い違う箇所は本書内で明示する

## 記法

EARS（Easy Approach to Requirements Syntax）の5パターンを日本語で用いる。既存の CLOUDFLARE_MIGRATION.md §4 の言い回しに合わせ、述語は「〜しなければならない」で統一する。

| 種別 | 記法 |
|---|---|
| 遍在（Ubiquitous） | 〜は、〜しなければならない |
| 事象駆動（Event-driven） | 〜されたとき、〜は〜しなければならない |
| 状態駆動（State-driven） | 〜である間、〜は〜しなければならない |
| 望ましくない挙動（Unwanted） | もし〜ならば、〜は〜しなければならない |
| 任意機能（Optional） | 〜が有効な場合、〜は〜しなければならない |

要件IDは `FE-nnn` で安定。既存IDの番号を保つため、後から挿入した要件には `FE-031a` のように英字サフィックスを付ける。付録Bに「現行Kotlinファイル → 要件ID」の対応表を置く。

**現行実装との関係**: 本書の要件は原則として現行実装の忠実な記述だが、既知の不具合については**修正後の仕様**を記述している。該当箇所には必ず「現行実装と異なる」旨の注記と付録Aへの参照を付けてある。意図的に異なる要件の一覧は付録A末尾にまとめてある。

## 1. ルーティング

| ID | 種別 | 要件 |
|---|---|---|
| FE-001 | 遍在 | フロントエンドは、`/`（トップ）、`/advertisers/{videoId}`（広告主リスト）、`/404`（Not Found）の3ルートを提供しなければならない。 |
| FE-002 | 事象駆動 | ブラウザが `/advertisers/{videoId}` へ直接アクセスしたとき、アプリケーションは該当動画の広告主リスト画面を描画しなければならない（配信側のSPAフォールバック設定が前提。CLOUDFLARE_MIGRATION.md §4-15と対応）。 |
| FE-003 | 事象駆動 | 検索フォームから有効な動画IDが送信されたとき、アプリケーションは `/advertisers/{videoId}` へ遷移しなければならない。このとき履歴は **PUSH**（新規エントリを追加）で更新しなければならない。 |
| FE-004 | 事象駆動 | 動画カードがクリックされたとき、アプリケーションは `/advertisers/{videoId}` へ遷移しなければならない。このとき履歴は **PUSH** で更新しなければならない。 |
| FE-005 | 事象駆動 | 広告主リスト画面のデータ取得でHTTP 404が返されたとき、アプリケーションは `/404` へ遷移しなければならない。 |
| FE-006 | 事象駆動 | 定義されたルートのいずれにも一致しないパスへアクセスされたとき、アプリケーションは404画面（FE-180／FE-181）を描画しなければならない。 |

> FE-006 は見落としやすい。配信側は `not_found_handling: "single-page-application"` により**未知のパスすべてに `index.html` を返す**ため、404画面の描画責務は完全にクライアントルーター側にある。Kobweb は暗黙にこれを行うが、React Router では `path="*"` のルートを明示しない限り何も描画されず、本番で白画面になる。

> **FE-003 は現行実装（REPLACE）と異なる。** 導線によって履歴モードが変わり検索後にブラウザバックできない現行挙動は不具合として扱い、PUSH に統一する（付録A-6）。

## 2. 共通レイアウト

| ID | 種別 | 要件 |
|---|---|---|
| FE-010 | 遍在 | 全ページは、ヘッダー・メインコンテンツ・フッターを縦に並べ、ページ全体の高さを最低 `100vh` としなければならない。メインコンテンツは残余高さを埋めなければならない（`flex-grow: 1`）。 |
| FE-011 | 遍在 | ヘッダーは、アプリ名「ニコニコ動画 広告主リスト取得」を `/` へのリンクとして表示しなければならない。 |
| FE-012 | 状態駆動 | 投稿者IDが設定されている間、ヘッダーは投稿者アイコン画像（円形・32px）を表示しなければならない。設定されていない間は人型アイコンを表示しなければならない。 |
| FE-013 | 事象駆動 | ヘッダーの投稿者アイコンがクリックされたとき、アプリケーションは投稿者ID設定ダイアログを開かなければならない。 |
| FE-014 | 遍在 | ヘッダーは、カラーモード切り替えコントロールを表示しなければならない。 |
| FE-015 | 遍在 | フッターは、注意書き「このツールは非公式のファンツールです」、`https://x.com/numa_radio` への「@numa_radio」リンク、`https://github.com/numa08/niconico-advertiser-list2` への「GitHub」リンクを表示しなければならない。外部リンクは `target="_blank"` かつ `rel="noopener noreferrer"` でなければならない。 |
| FE-016 | 遍在 | 投稿者アイコンのURLは `https://secure-dcdn.cdn.nimg.jp/nicoaccount/usericon/{prefix}/{userId}.jpg` でなければならない。`prefix` は `floor(userId / 10000)` を10進表記した値とする。 |
| FE-017 | 遍在 | 投稿者IDはアプリケーション全体で単一の状態として保持されなければならない。ヘッダーのダイアログから保存または解除されたとき、ヘッダーのアイコン表示とトップページの表示（動画一覧の取得を含む）は、再読み込みを要さず即座に更新されなければならない。 |
| FE-018 | 望ましくない挙動 | もし投稿者アイコン画像の読み込みに失敗したならば、ヘッダーは代替として人型アイコンを表示しなければならない。 |

> **FE-016 は現行実装（先頭2文字）と異なる。** 現行の規則は6桁のIDでは偶然一致するが、他の桁数で破綻する（付録A-5）。この規則は実測で確認済み — 検証方法と結果は付録Eを参照。
>
> **FE-017 は現行実装にない。** 現行はヘッダーとトップページが投稿者IDの状態を独立に保持しており、ヘッダーから設定しても動画一覧が読み込まれない（付録A-1）。
>
> FE-018 は FE-016 の修正に伴う保険。退会済みユーザーなどアイコンが存在しないケースで壊れた画像を出さないための追加要件。

## 3. テーマ・スタイル

| ID | 種別 | 要件 |
|---|---|---|
| FE-020 | 遍在 | アプリケーションは、ライト／ダークの2テーマを持ち、付録CのカラートークンとColorPalette値を再現しなければならない。 |

| FE-025 | 任意機能 | ユーザーが動きの低減を要求していない場合（`prefers-reduced-motion: no-preference`）、アプリケーションはスムーススクロールを有効にしなければならない。 |
| FE-026 | 遍在 | 主要コンテンツ（検索フォーム・動画情報・広告主リスト・エラー表示）は最大幅 `600px`、投稿動画一覧は最大幅 `900px` で中央寄せしなければならない。 |
| FE-027 | 遍在 | サムネイル画像は 160×90px、`object-fit: cover`、角丸4pxで表示しなければならない（FE-028が適用される幅を除く）。 |
| FE-028 | 状態駆動 | ビューポート幅が `640px` 未満である間、アプリケーションは以下のレイアウトを適用しなければならない。<br>・動画情報カード（FE-081）および動画カード（FE-037）は、サムネイルとテキストを**縦積み**にし、サムネイルは幅100%・アスペクト比16:9で表示する<br>・ページ左右の余白を `2rem` から `1rem` に縮小する<br>・検索フォームの入力欄と「検索」ボタンを縦積みにし、ボタンは幅100%とする |
| FE-029 | 遍在 | ページ本文は、いかなるビューポート幅でも横スクロールを発生させてはならない。整形済み広告主リスト（FE-083）のように内容が収まらない要素は、その要素の内部でスクロールさせなければならない。 |

> **FE-028／FE-029 は現行実装にない要件**（現行はブレークポイントを持たず最大幅指定のみ）。React 移行に合わせて追加する（付録A-8）。ブレークポイント `640px` は本移行での新規決定であり、既存コードに根拠は無い。

| FE-034 | 状態駆動 | 投稿動画の取得中である間、トップページは「読み込み中...」を表示しなければならない。 |
| FE-035 | 遍在 | 動画一覧は、取得件数を「{videosCount}件の動画」の形式で表示しなければならない。 |

## 7. 広告主リストページ `/advertisers/{videoId}`

### 7.1 データ取得

| ID | 種別 | 要件 |
|---|---|---|
| FE-070 | 事象駆動 | ページのURLパラメータ `videoId` が確定したとき、アプリケーションは `GET /api/video/info?videoId={videoId}` と `GET /api/video/nicoad-history?videoId={videoId}` を**並列に**発行し、両方の完了（広告履歴はFE-070aの全チャンク取得完了）を待ってからローディング状態を解除しなければならない。 |
| FE-070a | 状態駆動 | 広告履歴レスポンスに `nextOffsetId` が含まれている間、アプリケーションは `offsetId={nextOffsetId}` を付与して `GET /api/video/nicoad-history` を繰り返し呼び出し、各レスポンスの `histories` を受信順に連結しなければならない。`nextOffsetId` を含まないレスポンスを受けたとき、それまでの連結結果をもって広告履歴の取得完了としなければならない。ループ中の各リクエストには初回リクエストの `refresh` 指定を引き継がなければならない。暴走防止のため、継続リクエストは最大25回（約10万件）で打ち切らなければならない。 |
| FE-071 | 状態駆動 | 取得中である間、ページは「読み込み中...」を表示しなければならない。 |
| FE-072 | 望ましくない挙動 | もしいずれかのリクエストがHTTP 404を返したならば、アプリケーションは FE-005 に従い `/404` へ遷移しなければならない（エラーメッセージは表示しない）。 |
| FE-073 | 望ましくない挙動 | もし404以外のエラーが発生したならば、アプリケーションは発生したエラーメッセージを `"; "` で連結して表示しなければならない。 |
| FE-074 | 状態駆動 | 動画情報または広告履歴のいずれかを保持している間、ページは「データを更新」ボタンを表示しなければならない。 |
| FE-075 | 事象駆動 | 「データを更新」が押下されたとき、アプリケーションは両APIを `refresh=true` 付きで並列に再取得し、完了までボタンを無効化しラベルを「更新中...」に変更しなければならない。 |
| FE-076 | 遍在 | 「データを更新」ボタンは、初回取得中および更新中は無効でなければならない。 |
| FE-077 | 状態駆動 | 動画情報と広告履歴の少なくとも一方が `cachedAt` を保持している間、ページは「キャッシュ: {利用中\|更新済} ({日時})」を表示しなければならない。日時は存在する `cachedAt` のうち**より古い方**とし、`null` の側は比較から除外しなければならない（片方のみ存在する場合はその値を用いる）。両方が `null` の間は本表示を行ってはならない。 |

## 付録D: 整形アルゴリズムのテストベクタ

React 実装のユニットテストへそのまま移植すること。

### D-1: 基本的な折り返し（FE-105〜FE-107）

入力: 名前リスト `["あ様", "い様", "う様", "え様"]`、1行の文字数 `6`

```
あ様、い様、
う様、え様
```

導出:
- `あ様、`(3) → 行「あ様、」
- `い様、`(3) → 3+3=6 は 6 を超えないため同一行「あ様、い様、」
- `う様、`(3) → 6+3=9 > 6 かつ行が非空 → 改行。行末の `、` は残る
- `え様`(2、最終要素なので区切りなし) → 3+2=5 で同一行

### D-2: 1行の文字数を超える単一要素（FE-108）

入力: `["あいうえおかきくけこ"]`、1行の文字数 `1`
出力: `あいうえおかきくけこ`（分割しない）

### D-3: 重複除去＋逆順の順序（FE-104）

入力（APIの返却順）: `[A, B, A, C]`、形式 `同じ名前をまとめる（逆順）`、敬称 `様`
- 重複除去（最初の出現を残す） → `[A, B, C]` → 逆順 → `[C, B, A]`
- 期待出力: `C様、B様、A様`

この順序は現行 Kotlin 実装の挙動と**意図的に異なる**。現行は `逆順→重複除去` で `[C, A, B]` → `C様、A様、B様` を返すが、これはバグである（付録A-13）。React 実装ではこのベクタが通ることを確認し、Kotlin 版との出力一致テストをここに適用してはならない。

### D-4: 重複除去（FE-103）

入力: `[A, B, A, C]`、形式 `同じ名前をまとめる` → `[A, B, C]`（最初の出現を残す）

### D-5: 1行の文字数のフォールバック（FE-109）

| 入力 | 使用される値 | 現行Kotlin実装 |
|---|---|---|
| `"50"` | 50 | 50 |
| `""` | **50** | 1 |
| `"abc"` | **50** | 1 |
| `"0"` | 1 | 1 |
| `"-5"` | 1 | 1 |

「使用される値」列が FE-109 の期待値。現行実装列は参考であり、空欄・非数値の2ケースは意図的に異なる。

### D-6: カスタム敬称（FE-100）

敬称 `カスタム`／カスタム入力 `殿` → `名前殿`。カスタム入力が空文字なら `名前`（敬称なし）。

### D-7: サロゲートペアの文字数カウント（FE-105）

広告主名には絵文字が日常的に含まれるため、文字数の数え方の差がそのまま折り返し位置の差になる。

入力: 名前リスト `["🎉様", "🎉様"]`、敬称は空、1行の文字数 `5`

期待出力（UTF-16コード単位でカウント。`🎉` は2単位）:

```
🎉様、
🎉様
```

- `🎉様、` = 4単位 → 0+4 は 5 を超えないので同一行
- `🎉様` = 3単位 → 4+3=7 > 5 なので改行

コードポイント数（`[...s].length`）や `Intl.Segmenter` で数えると `🎉様、` = 3、`🎉様` = 2 となり、3+2=5 は 5 を超えないため **1行にまとまってしまい不一致**となる。

### D-8: 投稿者アイコンURL（FE-016）

| userId | 期待するURL |
|---|---|
| `753685` | `.../usericon/75/753685.jpg` |
| `1594318` | `.../usericon/159/1594318.jpg` |
| `13647798` | `.../usericon/1364/13647798.jpg` |
| `134979178` | `.../usericon/13497/134979178.jpg` |

`753685` は現行の「先頭2文字」規則でも同じ結果になるため、**これ単独では回帰テストにならない**。7桁以上のケースを必ず含めること。

### D-9: 区切り文字（FE-096, FE-097, FE-100a, FE-105）

区切り文字の解決:

| 選択 | カスタム入力 | 使用される区切り文字 |
|---|---|---|
| `読点（、）` | （無視） | `、` |
| `句点（。）` | （無視） | `。` |
| `カスタム` | `" / "` | `" / "` |
| `カスタム` | `""` | `""`（区切りなし） |

整形への反映（敬称 `様`、名前リスト `[A, B, C]`）:

| 区切り文字 | 1行の文字数 | 期待出力 |
|---|---|---|
| `。` | 50 | `A様。B様。C様` |
| `""` | 50 | `A様B様C様` |
| `" / "` | 6 | `A様 /`＋改行＋`B様 /`＋改行＋`C様` |

`" / "` のケースは、区切り文字も文字数計算に含まれること（`A様 / ` は4文字。次要素を足すと 4+4=8 > 6 で改行）と、
行末の空白がtrimで除去されること（FE-107）を同時に示す。区切り文字は最終要素の末尾には付与しない。

## 付録E: 投稿者アイコンURL規則の実測検証（FE-016 / 付録A-5）

FE-016 の prefix 規則は推測ではなく実測に基づく。検証日: 2026-07-31。

**方法**: nvapi のランキングAPI（`GET https://nvapi.nicovideo.jp/v1/ranking/genre/all?term=24h&pageSize=100`、`X-Frontend-Id: 6` 必須）から、実在する投稿者の `owner.id` と `owner.iconUrl` の組を取得し、URL 中の prefix セグメントを2つの規則と突き合わせた。チャンネル（`ch` 始まりのID）は投稿者アイコンとは別系統（`comch/channel-icon/...`）のため除外した。

**結果**（ユーザーアイコンを持つ実在ID 62件、桁数5〜9桁）:

| 規則 | 一致 |
|---|---|
| `floor(userId / 10000)` | **62 / 62** |
| 先頭2文字（現行実装） | 7 / 62 |

先頭2文字が一致した7件はいずれも6桁のIDで、両規則の結果が偶然一致するケースだった。

**補足**:

- 実際の `iconUrl` には `?1546415269` のようなキャッシュバスター用クエリが付くが、クエリなしでも画像は 200 で取得できる。付与は不要
- アイコンを設定していないユーザーは `https://secure-dcdn.cdn.nimg.jp/nicoaccount/usericon/defaults/blank.jpg` を返す。FE-018 のフォールバックはこのケースおよび退会済みユーザーを想定している
